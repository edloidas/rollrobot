# Deployment

Roll Robot runs as one Cloudflare Worker behind a Telegram webhook. This document covers a
first deploy end to end; day-to-day releases are just `bun run worker:deploy`, or a `v*` tag
if you want CI to do it.

## How it fits together

The Worker exposes exactly two routes:

| Route | Purpose |
| --- | --- |
| `GET /health` | Liveness probe. Returns `OK`. |
| `POST /webhook` | Telegram updates. Rejected with `401` unless `X-Telegram-Bot-Api-Secret-Token` matches `WEBHOOK_SECRET`. |

Anything else is a `404`. There is no state between requests — the bot instance is cached
per isolate and rebuilt whenever the token or the webhook secret changes.

Deployment never registers or modifies the Telegram webhook. Pointing Telegram at a Worker
is a separate command you run once, and again whenever the Worker URL changes. Keeping the
two apart means a bad deploy cannot silently repoint a live bot.

## Secrets

Three encrypted Worker secrets, all set through `wrangler secret put`:

| Key | Description |
| --- | --- |
| `TOKEN` | Bot token generated by BotFather. |
| `WEBHOOK_SECRET` | Random value Telegram echoes back on every update, used to authenticate the webhook. |
| `ANALYTICS_SALT` | Random value used to hash Telegram user IDs before they reach analytics. |

All three are listed under `secrets.required` in `wrangler.jsonc`, so Wrangler refuses to
deploy or upload until each one is set. That is deliberate for `ANALYTICS_SALT`: a Worker
running without it does not skip analytics, it writes every row with an empty digest, and
those rows are permanently un-attributable — the report filters them out and there is no
backfill.

## Cloudflare setup

Install dependencies, authenticate Wrangler, generate the two random values, and store all
three secrets:

```sh
bun install
bunx wrangler login
openssl rand -hex 32
bunx wrangler secret put TOKEN
bunx wrangler secret put WEBHOOK_SECRET
bunx wrangler secret put ANALYTICS_SALT
```

Analytics Engine must be enabled once per Cloudflare account before the first deploy. The
`rollrobot_events` dataset itself is created implicitly on first write — there is nothing to
provision.

## Local environment

Create an ignored `.env` in the repository root. Bun loads it automatically for
`telegram:configure`, and Wrangler uses it for local Worker development:

```dotenv
TOKEN=0123456789:replace-with-telegram-bot-token
WEBHOOK_SECRET=replace-with-a-random-webhook-secret
ANALYTICS_SALT=replace-with-a-random-analytics-salt
WEBHOOK_URL=https://rollrobot.<account-subdomain>.workers.dev/webhook
```

Keep `.env` local. It does not upload anything to Cloudflare — the `wrangler secret put`
commands above are still required for the deployed Worker.

## Deploy

Run the Worker locally first, then deploy once `/health` and webhook authentication behave:

```sh
bun run worker:dev
bun run worker:deploy
```

`bun run worker:upload` publishes a version without routing traffic to it, for a staged
rollout from the Cloudflare dashboard.

## Telegram configuration

After the first deploy, put the real Worker URL in `WEBHOOK_URL` and register it:

```sh
bun run telegram:configure
```

The command registers `message`, `inline_query`, and `chosen_inline_result` updates, and
publishes the localized command menu and bot descriptions. It preserves queued updates
unless `DROP_PENDING_UPDATES=true` is explicitly set — a redeploy should not discard rolls
people already sent.

Inline mode and inline feedback are BotFather settings, not API ones. `/setinline` must be
on for `@rollrobot [notation]` to work at all, and `/setinlinefeedback` controls what share
of inline rolls are reported back — see [ANALYTICS.md](ANALYTICS.md#inline-rolls-are-undercounted).

## Verify

```sh
curl "https://rollrobot.<account-subdomain>.workers.dev/health"
curl "https://api.telegram.org/bot<telegram-bot-token>/getWebhookInfo"
```

`getWebhookInfo` should show the Worker URL, no `last_error_message`, and a
`pending_update_count` that drains to zero. Then exercise all four surfaces — private chat,
group, supergroup, and inline — and watch the Worker logs. When Telegram refuses a group
reply with a `403` about missing rights, the bot direct-messages the sender instead of
failing silently; other refusals are logged only, so the logs are the place to look.

## Releases

Tagging `v*` on `master` runs the release workflow: it verifies the tag commit is on
`master`, runs `bun run validate`, deploys the Worker, and creates a GitHub Release. A tag
carrying a hyphen (`v3.3.0-rc.1`) is published as a prerelease. The full version-bump
sequence is in [CLAUDE.md](CLAUDE.md#releases).

CI needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as repository secrets; the token
needs the **Edit Cloudflare Workers** template.
